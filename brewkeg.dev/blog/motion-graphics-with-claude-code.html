How to make motion graphics with Claude Code (no After Effects)

One HTML file, a browser and a prompt. The rules that separate a loop people watch from a loop that stutters, plus example loops and a render workflow.

2026-11-20·#guides#workflow#motion

You do not need After Effects to make motion graphics anymore. You need one HTML file, a browser, and a prompt.

The catch: a model will happily build you a loop that stutters, drops frames, and puts your hero the size of a dot. Most of those loops get posted and forgotten.

These are the rules that fix that. They are model-agnostic. They work on Claude Code, Codex, or anything else you point at the endpoint.

Many models can generate motion-graphics code (HTML/Canvas/WebGL you render frame by frame). Stronger models can make the workflow easier, but no single model “revolutionized” it. Results come from a deterministic renderAt(t) contract, specific numbers, and measured QA.

Example loops

Short loops from the playbook that inspired this post (see the original thread/article). Same ingredients: a time contract, numbers instead of adjectives, and frame-by-frame rendering.

1. Give the model a contract, not a wish

The whole trick is one function. If the model exposes renderAt(t), an agent can draw any single frame on its own, check it, and fix it. If it animates with a running clock, nothing can be checked and the render will drift.

Put that in the prompt as written and tell the model not to change it. Every other rule below depends on this one.

2. Replace every adjective with a number

The model cannot read "premium". It can read roughness 0.38.

Instead ofWrite
premiumroughness 0.38, clearcoat 0.35
cool lightkey 3200 K, rim 7500 K
modern35 mm, f/2.8, cut on the beat
smoothcubic-bezier(0.16, 1, 0.3, 1)
bouncyspring, damping 0.5, 2 bounces
fast cutscut on the beat: frames per beat = fps × 60 / BPM

A vague brief on a precise model gives you a precise default. Every adjective you swap for a number raises the quality one step.

3. Pick the right effort

For motion work, High effort is usually the sweet spot. Max can think longer and cost more without making the film reliably better.

Use High for directed builds and fixes. Use a cheaper model for storyboards, stills, and shot planning, then switch up only for the final unattended build.

4. One number decides how a landing feels

"Bouncy" is a mood. 0.5 is an instruction.

None of them is wrong. Each one is right for a different job, and the number picks the job.

Two things to add alongside it:

  • Closed form, not integrated. A spring that adds velocity every frame gives a different landing when the renderer jumps to frame 300. Say: every spring is a closed-form function of t, no integration across frames.
  • Squash and stretch, volume kept. Crouch 1.2×0.75, takeoff 0.85×1.28, landing 1.25×0.75.

5. Render on the GPU, frame by frame

Screen recording drops frames. This does not. Save it as render.py next to film.html, serve the folder with python -m http.server 8000, then run it.

Want motion blur? Render 8 to 32 sub-frames per frame and average them. It multiplies render time by the same factor.

6. Stills lie. Measure motion.

This is the rule people skip, and it is the one that saves the most time. A checker that looks at still frames will happily pass a film with a hundred seconds of frozen graphics in it.

And the rule no tool replaces: press play yourself, on anything that moves or makes sound.

7. Write the timing first, define "done"

Before any code, have the model write the beat grid and the shot list as text. Then animate against it.

"Done means the loop runs and every check passes" is worth more than three paragraphs of taste. A model told to be done will be done. A model given a checklist will finish.

Two more that pay for themselves:

  • Design clipping out. Give every moving thing a lane it cannot leave. A collision you made impossible never needs a fix.
  • Never let the model type a time. Make a command read the clock and write it.

8. Iterate cheap, build expensive

The expensive tier is not the better tier for the whole job. Storyboards, stills and "talk through this shot" are the same work on a cheap model. The long unattended build is where the big model earns its keep.

So: plan on brewkeg-nano or brewkeg-pro, then switch to brewkeg-ultra right before you say "build it".

Two traps, and both cost real money:

  • Scripts bill without asking. Once you have switched a session to a big model, later claude -p runs inherit it. Pin --model in every script.
  • Iterating on stills is nearly free. Iterating on renders is not. One fix round on stills before the first full render saves more than any prompt trick in this post.

Because brewkeg is metered, you can see exactly what each run cost, and the credit you do not spend is still there next month. That is the part a monthly quota hides from you.

Common failure modes

  • Frozen hero or tiny subject: measure the hero in pixels per shot and set a minimum size.
  • Seam jump on loop: force frame N-1 to flow into frame 0 for pose, velocity, camera, and light.
  • Drift on re-render: keep renderAt(t) pure. No clocks, no randomness, no state carried across frames.
  • "Looks good" QA: require numbers in the report (freeze spans, seam delta, hero width, seek parity).

The contract, the numbers and the QA loop are the whole skill. Everything else is taste, and taste you can now specify.
